# ADR-0011 — LLM 호출 회복탄력성 계층 (재시도 + 구조적 에러 + 사용자향 메시지)

| 항목 | 내용 |
|------|------|
| **상태** | 수용됨 (P-2, 2026-08) |
| **결정자** | 프로젝트 오너 |
| **관련** | ADR-0004(LLM 경계), ADR-0008(출력 렌더 안전) |

---

## Context

agent(챗 루프)와 summarizer가 각자 Anthropic `/v1/messages`에 blocking POST 하고,
에러를 즉석에서 처리했다. 문제:

1. **raw JSON 노출** — 529 overloaded 등 비-429 실패 시 `format!("API 오류 {status}: {text}")`로
   응답 본문(JSON)을 사용자 챗에 그대로 표시했다.
2. **재시도 없음** — 529/429는 대개 일시적인데, 한 번 실패하면 그대로 끝났다.
3. **중복** — 같은 호출·에러 처리 코드가 두 곳에 있었다.
4. **디버깅 단서 유실** — Anthropic `request-id`를 보존하지 않았다.

---

## Decision

**Anthropic 호출을 공유 계층 `llm_http`로 묶고, 일시적 오류는 제한 재시도로 자동 복구하며,
실패는 사용자향 메시지로 변환한다. request_id는 로그에만 남긴다.**

- **테스트 가능한 재시도 오케스트레이터** — `retry_with_backoff(max, sleep, attempt)`는 HTTP를
  모른다. `sleep`을 주입받아 테스트에서 no-op으로 즉시 실행한다. `attempt`는 1회 시도 클로저.
- **구조적 에러** — `ApiError { kind, request_id, detail }`. `kind`는 상태코드로 분류:
  `Overloaded(529)`/`RateLimited(429)`/`ServerError(5xx)`/`Network`(재시도) vs
  `Auth(401·403)`/`Client(그 외 4xx)`/`Parse`(비재시도).
- **재시도 정책** — `is_retryable()`가 true인 것만 지수 백오프(1s→2s→4s), 최대 3회.
- **사용자향 메시지** — `user_message()`는 kind별 한국어 문구만 반환하며 `detail`(raw JSON)·
  `request_id`를 절대 포함하지 않는다.
- **로그 보존** — 재시도·최종 실패 시 `kind`·`request_id`·`detail`을 `eprintln!`로 남긴다(비노출).
- **공유** — agent `complete`와 summarizer가 `anthropic_post_with_retry`를 함께 쓴다. agent는
  `ApiError → user_message()`, summarizer는 `ApiError → SummaryError`로 매핑.
- **프론트** — 에러 버블(API 키 문제 제외)에 "↻ 다시 시도" 버튼. 마지막 사용자 메시지를
  버블 중복 없이 재전송한다.

---

## Consequences

**긍정**

- 일시적 529/429가 사용자 개입 없이 자동 복구된다(대부분).
- 사용자는 raw JSON 대신 이해 가능한 문구를 본다(ADR-0008의 "신뢰 불가 출력 렌더" 원칙과도 정합).
- 재시도로도 안 풀리면 사용자가 버튼으로 재시도할 수 있다.
- 호출·에러 로직이 한 곳에 모여 일관적이고, 재시도 로직은 HTTP 없이 단위 테스트된다.

**비용**

- blocking + `std::thread::sleep` 재시도라 최악의 경우 호출이 최대 1+2+4초 지연될 수 있다
  (데스크톱 앱의 chat 커맨드는 이미 blocking이라 수용 가능).
- 재시도 상한(3회)·백오프 값은 하드코딩. 필요 시 설정화는 후속.

**관련 코드 경로**
