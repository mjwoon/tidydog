# TidyDog 안전 명세

> 코드 현실 역반영 문서(T2). 구현 소스: `crates/tidydog-core/`, `src-tauri/src/`.  
> 이 문서에 없는 동작은 구현되지 않은 것으로 간주한다.

---

## 핵심 불변식

1. **파일을 바꾸는 유일한 경로는 `Engine::execute`.**  
   Tauri 커맨드, 스캐너, 요약기, 위키 생성기 어느 것도 이 경로를 우회하지 않는다.
2. **영구삭제 코드가 없다.**  
   `Action` 열거형에 Delete 변종이 없다. 삭제는 `Action::Stage`(소프트)뿐이며 복원 가능하다.
3. **덮어쓰기 금지 (C4).**  
   목적지 충돌은 `Engine::resolve_conflict`가 `name (n).ext` 리네임으로 처리한다.

## Phase 1-2 안전 속성

### S1 — op 단위 내구성

`execute` 루프에 트랜잭션 래퍼가 없다. 각 SQL(`append_journal`, `complete_journal`, `set_plan_status`)은 autocommit으로 즉시 내구화된다.

부분 실패 시: 앞선 op들의 journal은 살아있고 undo 가능하며, 실패한 op의 intent는 `completed_at=NULL`로 DB에 남아 crash recovery 대상이 된다 (`GateError::PartialExecute`).

### S2 — Journal-first

각 op 실행 순서:

```
1. append_journal(completed_at=None)  ← intent 기록, autocommit
2. move_file() / stage_file()         ← 파일 작업
3. complete_journal(entry_id, ts)     ← 완료 확정, autocommit
```

파일 작업 실패 시 intent(completed_at=NULL)는 DB에 남는다. `recover_inflight`가 정리한다.

### S3 — Crash recovery (`recover_inflight`)

앱 시작 직후 `.setup()` 훅에서 `recover_inflight(conn, staging_dir)` 실행.

`completed_at IS NULL` 항목을 FS와 대조:

| FS 상태 | 처리 |
|---------|------|
| `to` 경로에 파일 있음 | `complete_journal(entry_id, ts)` — 작업 완료됐으나 기록 누락 |
| `from` 경로에 파일 있음 | `DELETE FROM journal` — op 시작 전 크래시, intent 제거 |
| 양쪽 없음 | `complete_journal` + 경고 — 손실 이미 발생 |

### S4 — 스코프 가드 (TOCTOU 방지)

`execute` 2단계에서 모든 op의 from/to를 가드로 **재검증**한다(propose 시점과 별개).

`ScopeGuard` 블랙리스트 (macOS 기준): `/System`, `/usr`, `/bin`, `/sbin`, `/private`, `/Library`, `~/Library`, `~/.Trash`, `~/.ssh`, `~/.gnupg`.

숨김 경로(dotfile, `node_modules`) 자동 차단.  
심링크 탈출: `canonicalize()`로 실경로 해소 후 화이트리스트 체크.

### S5 — BLAKE3 cross-volume 검증

`FsFileOps::move_file`: `fs::rename` 성공 시 종료. cross-device 에러 시 `fs::copy` 후 양쪽 BLAKE3 해시 비교 → 불일치 시 `copy_failed_hash_mismatch` 에러. 성공 후 원본 삭제.

### S6 — Staging = 앱 관리 디렉터리 (OS 휴지통 아님)

`Action::Stage`의 실제 목적지: `app_data_dir/staging/{content_hash}`.

macOS `trash` 크레이트의 `restore_all`이 macOS에서 컴파일 불가(`#[cfg(not(target_os="macos"))]`)이므로 커스텀 staging 디렉터리로 구현.

`restore_file(content_hash, to)`: staging 디렉터리에서 exact match → prefix scan(`{hash}_*`) 순으로 탐색 후 원위치로 이동.

### Undo 윈도우 (C5)

`UNDO_WINDOW = 5`. 최근 5개 실행 플랜만 undo 가능.  
`undo`는 journal에서 `completed_at IS NOT NULL` 항목만 역실행 (in-flight 건너뜀).

## Phase 3 안전 속성 (N1–N5)

### N1 — 콘텐츠 전송 동의 게이트

**사용자 명시적 동의 없이 파일 내용을 클라우드로 전송하지 않는다.**

동의 게이트 위치: `index_file_content` 커맨드 진입 직후, 사이드카 프로세스 실행 이전.

```
db 초기화
  ↓
[N1 gate] CloudSummarizer::is_consented() 체크   ← 여기서 차단
  ↓ (동의 없으면 즉시 Err 반환)
SidecarReader::read_content()                     ← 파일 내용 읽기
  ↓
CloudSummarizer::summarize()                      ← API 전송
```

`is_consented()` 구현: `SELECT value FROM settings WHERE key='ai_content_consent_granted'` → `'true'`일 때만 true. 행 없음 / `'false'` → false.

동의 설정 커맨드: `set_ai_consent(granted: bool)`.

`summarize()` 내부에서도 `is_consented()` 재확인 (방어적 이중 체크).

**테스트 증명**: `summarizer.rs::tests::n1_no_consent_row_returns_not_consented`, `n1_consent_false_returns_not_consented`.

### N2 — API 키 OS 키체인 저장

API 키는 OS 키체인에만 저장된다. 평문 파일, 코드, 로그, 환경 변수에 절대 남기지 않는다.

구현:
- 저장: `keyring::Entry::new("tidydog", "anthropic_api_key").set_password(key)`
- 조회: `entry.get_password()` — `summarize()` 호출 때마다 실시간 조회 (struct에 저장 안 함)
- 에러 메시지에 키 값 미포함 (고정 문자열: `"no API key stored — use set_api_key command"`)

`.gitignore`에 `.env`, `.env.*`, `*.key`, `*.secret` 포함.

커맨드: `set_api_key(key: String)`.

### N3 — 전송 분량 최소화

클라우드로 보내는 텍스트는 `ContentBudget::default()` 이하로 제한한다.

| 파라미터 | 값 |
|---------|-----|
| `max_chars` | 4096 |
| `max_pages` | Some(5) |

사이드카(`reader.py`)가 페이지 단위 추출 시 `max_chars` 도달하면 중단, `truncated=true` 반환.  
`CloudSummarizer::call_api()`는 `chunk.text`(이미 예산 내)를 그대로 전송한다.

**테스트 증명**: `reader.rs::tests::n3_budget_enforced_large_file` (8000자 → max_chars=100 → len≤100, truncated=true).

### N4 — read_level 스코프 가드

`files.read_level='content'`는 `index_file_content`가 **성공적으로 완료된 파일에만** 설정된다.

경로: 사이드카 에러 → `?` 조기 반환 → `UPDATE files SET read_level='content'` 미도달.

깨진 PDF, 이미지 PDF, 존재하지 않는 파일: `ReaderError::ParseFailed` 또는 `ReaderError::SidecarUnavailable` 반환 → `read_level` 여전히 `'metadata'` (또는 NULL).

**테스트 증명**: `reader.rs::tests::broken_pdf_returns_err_not_content_chunk`, `missing_file_returns_err`.

### N5 — 사이드카 읽기 전용

`sidecar/reader.py`는 파일 내용을 읽기만 한다. 소스 파일을 수정·이동·삭제하는 호출이 없다.

`SidecarReader` 역시 경로를 사이드카에 전달하고 결과를 받는 것 외에 파일시스템 조작을 하지 않는다.
